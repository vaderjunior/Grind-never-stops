# P1 — URL shortener

A code names exactly one immutable destination; successful create survives restart. Cache loss may add latency but cannot change a redirect.

This prepared teaching lab uses Python 3.11+ standard-library modules. It is separate from the academy learner database. Read [the shared lab instructions](README.md) before running commands. Reference tests have been executed; learner TODOs are intentional work.

## Requirements and mechanism

- Accept only bounded HTTP(S) destinations without embedded credentials. Return a collision-safe code and a persistent redirect.
- Support optional expiration; expired values must fail even when cached. Cache is derived, never authoritative.
- Measure operations and skew locally. Demonstrate partition reassignment without claiming that the simulation moves durable data.

POST /links → validated create → SQLite unique code; GET /code → cache → SQLite fallback → 302. Rendezvous assignment is a separate deterministic partition simulation.

**Limits:** Single-machine SQLite, immutable links, an in-process cache, and a teaching HTTP harness. No abuse classifier, cross-node replication, account service, or distributed migration is implemented.

## Milestone 1 · Lesson 039 · Persistent create and redirect

Source activity: [P1.1] URL shortener: persistent create/redirect path and correctness tests

Implement create/resolve with a UNIQUE code constraint. Use the injected code factory to force a collision, retry at most ten times, and prove both destinations remain distinct after opening a second service instance. Validate destination protocol before any write.

**Failure injection:** A collision overwrites an existing destination in an unsafe INSERT OR REPLACE implementation. Inject repeated identical codes; the original mapping must remain unchanged.

**Acceptance evidence:** Persist two URLs, force a collision, reopen the database, and capture the exact redirect destinations.

## Milestone 3 · Lesson 069 · Partition movement and hotspots

Source activity: [P1.3] URL shortener: simulate partition movement and hotspot failures

Implement highest-score rendezvous assignment using SHA-256 of key plus node. Compare 1,000 keys on two nodes versus three. Identify which assignments change and explain why actual migration needs ownership epochs and read/write handoff.

**Failure injection:** Hash distribution balances distinct keys, not accesses. Repeating a viral key still concentrates requests on one owner; adding nodes alone does not split that key.

**Acceptance evidence:** Show every moved key selects the new node; report moved fraction and distinguish the simulation from a storage migration.
