# P3 — Job processing

Only the current unexpired claim token may commit a result. The local effect ledger and done state commit atomically; external side effects need their own idempotency boundary.

This prepared teaching lab uses Python 3.11+ standard-library modules. It is separate from the academy learner database. Read [the shared lab instructions](README.md) before running commands. Reference tests have been executed; learner TODOs are intentional work.

## Requirements and mechanism

- Persist bounded queued/running/done/dead states and unique job identities.
- Recover crashed workers through leases with fresh claim tokens, bounded retry backoff, and dead letters.
- Stop claiming during graceful shutdown, back up with SQLite backup API, and verify restored state.

enqueue → durable queue → lease claim with token → handler → transactional local result + done; failures → delayed retry → dead letter at limit.

**Limits:** Local workers share one SQLite database. The effect ledger proves only effects stored in the same transaction. An email or payment API outside this database is not exactly-once by this mechanism.

## Milestone 1 · Lesson 099 · Claims, execution and recovery

Source activity: [P3.1] Job system: implement claiming, execution, and recovery tests

Implement enqueue, claim and complete. Freeze time, claim a job, advance beyond its lease, and claim again. The second worker receives a different token. Reject completion from the first worker even though it once legitimately owned the job.

**Failure injection:** Worker A pauses beyond expiry while B reclaims. A resumes and attempts a stale commit. Checking only job ID would allow it; validate token, state and current lease within the commit transaction.

**Acceptance evidence:** Demonstrate stale-worker rejection, current-worker success, and one durable local effect.

## Milestone 3 · Lesson 148 · Graceful stop and bounded workers

Source activity: [P3.3] Job system: deployment, graceful shutdown, and bounded scaling

Add admission capacity and a worker drain loop with a stop event and maximum job count. A stop request prevents new claims while current work may finish. Define a termination grace period at least as long as bounded handler cleanup.

**Failure injection:** An unbounded queue moves overload into memory/storage and increases recovery time. A second enqueue into a full queue must fail explicitly without losing the accepted job.

**Acceptance evidence:** Run a full-queue test and a stopped-worker test; then drain one unit and show the capacity becomes available.
