# P4 — Chat backend

Authorized messages commit before acknowledgement and have a monotonically increasing sequence within each room. Live delivery is a hint; a cursor can recover committed messages.

This prepared teaching lab uses Python 3.11+ standard-library modules. It is separate from the academy learner database. Read [the shared lab instructions](README.md) before running commands. Reference tests have been executed; learner TODOs are intentional work.

## Requirements and mechanism

- Persist room membership, ordered message log, and sender-scoped idempotency keys.
- Support reconnect via seq > cursor, independently of lost pub/sub notifications.
- Use separate DB connections for concurrent workers and expiring presence that never grants authorization.

authenticated demo WebSocket → membership check → SQL append with room sequence → acknowledgement; live notification hints → reconnect query against authoritative log.

**Limits:** The supplied stdlib WebSocket scaffold supports bounded unfragmented text frames, ping/pong and close. Demo tokens are local test identities, not a production identity provider. Hub is an in-process lossy pub/sub stand-in shared by worker objects, not a multi-host broker.

## Milestone 1 · Lesson 173 · Persisted messaging on a transport scaffold

Source activity: [P4.1] Chat backend: persistent messaging over the supplied WebSocket scaffold

**Failure injection:** An acknowledgement sent before commit can lose a message after the sender stops retrying. A retry must return the existing sequence for identical content, while changed content under the same key conflicts.

**Acceptance evidence:** Send two messages, retry one, restart the store, and observe exactly two sequences in order.

## Milestone 3 · Lesson 188 · Multiple workers and presence expiry

Source activity: [P4.3] Chat backend: multiple workers, pub/sub, and presence expiry
